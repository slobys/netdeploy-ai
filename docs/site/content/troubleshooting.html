Windows 本地页面打不开

  1. 确认运行 NetDeploy 的 PowerShell 窗口还在，没有按 Ctrl+C。
  2. 打开 http://127.0.0.1:8787/api/health 检查后台版本。
  3. 若提示 8787 端口被占用，先停止旧实例，不要强行同时启动两个服务；之后按 Ctrl+F5 刷新网页。

SSH 连接被拒绝 / 超时

从 Windows PowerShell 检查：

Test-NetConnection YOUR_VPS_IP -Port 22

连接失败说明可能是云防火墙、VPS UFW、sshd 没监听、实例停机或地址/端口错误。连接成功但认证失败，才检查用户名、密码或 SSH 私钥。Google Cloud 用户先从云控制台的浏览器 SSH 入口排查。

3X-UI 安装第 5 步 SSH 握手失败（SSH_HANDSHAKE_FAILED）

如果日志显示第 4/5 步 Official installer finished，但第 5/5 步提示 SSH_HANDSHAKE_FAILED，说明安装器已返回成功，只是最终 SSH 连接和验收未完成。这不能证明 3X-UI 没安装，请勿直接重复安装或清空原配置。

  1. 更新 NetDeploy 并重启服务，刷新网页。新版会在执行远端命令之前最多尝试 3 次受信任的 SSH 连接；不会重复执行安装器、绕过主机指纹验证或自动重置 SSH。
  2. 打开原来的失败/待验收任务，点击 只读检查现有 3X-UI（不重装）。它仅通过已经核对指纹的 SSH 检查服务、实际监听和本机 HTTP 响应；如果面板在运行，可继续查看原来的管理地址和凭据。
  3. 如果 SSH 仍无法握手，请从云厂商浏览器控制台/串口检查 VPS 的 SSH 服务和负载。在 Ubuntu/Debian 的控制台可执行下面的只读检查命令：
sudo systemctl status ssh --no-pager
sudo systemctl status x-ui --no-pager
sudo ss -lntp | grep -E ':(22|8443)[[:space:]]'
sudo journalctl -u ssh -n 40 --no-pager

上面的 8443 是示例面板端口，请替换为你安装时填写的实际端口。SSH 握手失败可能与临时负载、连接限制、sshd 状态或算法协商有关，单凭这条错误无法确定根因。Test-NetConnection IP -Port 22 成功只说明 TCP 可达，不代表 SSH 协议握手正常。

如果提示 SSH_HOST_KEY_CHANGED 或 SSH_ALGORITHM_MISMATCH，NetDeploy 不会自动重试或跳过安全校验；请通过云服务商独立核对指纹或处理算法兼容性。面板自身即使已运行，云安全组仍须另外确认管理端口是否放行并限制来源 IP；公网明文 HTTP 有凭据泄露风险，建议用 NPM HTTPS。

SSH 指纹变化、信任失败

VPS 重装、系统更新了主机密钥、IP 发生回收都可能导致指纹变化。请从服务商独立控制台核对后使用 NetDeploy 的 SSH 安全 → 更新指纹；不要使用 StrictHostKeyChecking=no 绕过身份校验。

root 密码正确但仍无法登录

需要区分 root 本地密码、SSH 是否启用密码认证、root SSH 是否被禁用，以及 Google Cloud 的 OS Login/IAM 或 PAM 限制。见 谷歌云专题。修改 root 密码本身不等于开放 root SSH。

UFW 放行了，公网仍打不开

确认 VPS 真正监听对应端口、已通过有效 HTTPS / TLS 配置、云安全组的入站规则确实作用于目标实例，以及源 IP 和协议正确。Google Cloud 和 AWS 的 VPC 规则属于另一层网络控制。

3X-UI HTTPS 签证书失败

检查域名是否解析到该 VPS 公网 IP、TCP 80 是否可从公网访问、Certbot 续期服务是否正常，以及 3X-UI 实际监听与证书配置。如果软件已装好但 HTTPS 阶段失败，应使用 继续完成 HTTPS 创建修复计划，不必覆盖现有 3X-UI。

Debian 13 Certbot 4.0：IP 证书不支持

如果看到 Installed Certbot does not support IP certificates (requires recent Certbot 5.3+)，说明旧流程错误地使用了 Debian 13 软件源中的 Certbot 4.0。3X-UI 安装与 IP 证书是两个独立阶段：日志第 5/9 步已经通过，代表面板安装成功，只是 HTTPS 尚未完成。UFW_UNAVAILABLE 仅提示本机没装 UFW，不是该报错原因。

  1. 关闭旧 NetDeploy 窗口，更新并启动 v{{version}} 或更新版本，浏览器强制刷新。
  2. 选择原 VPS 的 3X-UI 卡片 → 查看已安装面板 → 继续完成 HTTPS；如果已有失败任务，请先重新生成当前版本的四步证书方案并审核。
  3. 系统自动从官方 PyPI 安装独立 Certbot 5.8.0，不会更改服务器原有的 /usr/bin/certbot 与系统续期计时器；IP 证书另用 /etc/netdeploy/letsencrypt 和 netdeploy-certbot-renew.timer。
  4. 确认 VPS 可通过 HTTPS 访问 PyPI、云厂商允许公网 TCP 80 进入 VPS，然后验收 HTTPS 面板访问及本机定时器运行。

如需在 VPS 控制台验证新环境是否准备完成，可运行以下只读命令；不要删除系统 Certbot、不要重装已经成功安装的面板。

sudo /opt/netdeploy-certbot/venv/bin/certbot --version
sudo systemctl status netdeploy-certbot-renew.timer --no-pager
sudo systemctl status x-ui --no-pager

若仍失败，记录新步骤的错误编号（例如 ND_CERTBOT_PYPI_FAILED 或 LE_HTTP01_UNREACHABLE）并检查出站 HTTPS、云厂商入站规则和 Let’s Encrypt 限流。

S-UI 安装后从公网打不开

新安装会尝试签发公网 IP/域名证书，只有证书、续期及 HTTPS 验证通过才会让管理 2095/TCP 监听公网。先在查看 S-UI 面板信息确认显示 HTTPS 直连地址；否则证书尚未生效，仍为本机访问。检查 TCP 80 ACME 验证、DNS A、公网 IP、Certbot 版本、云厂商安全组入站 2095/TCP 和有效证书；不要开放明文 HTTP。

如果 S-UI 已安装但 HTTPS 失败，保持原程序和凭据，到 S-UI 面板状态页点击继续完成 HTTPS即可创建四步证书修复任务，不必重新安装。订阅 2096/TCP 仍只监听本机。

3X-UI / S-UI 选择 NPM 后无法访问

检查安装计划是否选择「不申请证书，交给 NPM 反向代理」，此时不会运行 Certbot 或申请 IP/域名证书。新安装的 3X-UI NPM 模式会按审批开启公网 HTTP 管理端口；如果是旧版安装且仍只监听 127.0.0.1，在「已安装面板」中点击开启公网 HTTP（不申请证书）创建两步变更计划，不需要重装。完成后显示公网 IP、端口和原有 Web 路径；若外部打不开，还需检查云安全组 TCP 入站。S-UI 仍只监听宿主机本机地址。如果 NPM 是 Docker 普通 bridge 网络，容器内的 127.0.0.1 不是 VPS 宿主机，代理会出现 502。请按 NPM 统一 HTTPS 教程 将 NPM 设置为 Linux host 网络（移除 Compose 中 ports），让它反代宿主机回环地址。NPM 拥有 80/443、管理端 81，注意端口冲突和云防火墙来源白名单。

Dockge Apps：Docker、端口与公网访问

新版本在没有 Docker 的干净 Debian/Ubuntu VPS 上，使用 https://get.docker.com 官方一键脚本安装 Docker，再验证 Compose v2。若存在旧数据、冲突软件包或非完整 Docker 环境，则停止自动安装以保护已有容器。

管理端口留空自动随机生成，填写则按输入端口部署。遇到 DOCKGE_PORT_BUSY 或 DOCKGE_ACCESS_PORT_BUSY，可换一个端口后重新生成计划，不要强行结束其他服务。

Dockge Apps 新安装默认生成 http://服务器公网IP:端口/ 访问方案，安装页不再显示访问方式选项，公网风险会在部署审批页提示。已安装实例仍能在管理面板点击修改端口与访问方式。若公网链接打不开，检查对应 TCP 端口的云安全组入站规则；目前未自动配置 HTTPS，必须限制来源 IP 并尽快设置管理员。

docker ps --filter name=netdeploy-dockge-apps
docker logs --tail 50 netdeploy-dockge-apps
docker compose version

计划提示失效或需要刷新

如果服务器重装、SSH 主机密钥更换、证书域名或安装固定脚本发生变化，历史审批不再有效。可返回服务器控制台重新环境检测、刷新方案、再次审核。已有部分安装时先检查真实 VPS 状态，避免重复执行。

如何反馈故障

在 GitHub Issues 留下：NetDeploy 版本、VPS 系统、CPU、执行项目、出错阶段和脱敏的最后一步错误。禁止上传 SSH 密码、Token、证书私钥、管理员初始密码或完整 .env。
